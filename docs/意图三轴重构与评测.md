# EchoMind 意图三轴重构与评测

## 为什么重构

旧标签把三种不同问题混在同一层：

- 业务领域：`technical`、`billing`、`account`
- 用户动作：`query`、`request`、`complaint`、`feedback`
- 对话控制：`greeting`、`escalation`、`other`

例如“退款没到，立刻接人工”既属于账单领域，也在投诉，并要求人工接管。强迫三个标签争夺一个主意图，会造成标注歧义和虚假的分类错误。

## 新标签规范

### Domain（可多选）

| 标签 | 定义 | 正例 | 反例 |
|---|---|---|---|
| `technical` | 校园网、认证页面、连接和技术错误 | “校园网提示401” | “校园卡重复扣款” |
| `billing` | 校园卡、充值、消费、扣款和退款 | “充值没有到账” | “账号密码忘了” |
| `account` | 账号、密码、身份和个人资料 | “账号被锁定” | “网络延迟高” |
| `general` | 不属于三个专业领域 | “工单状态有哪些” | 不能与专业领域同时出现 |

### Action（单选）

| 标签 | 定义 | 正例 | 反例 |
|---|---|---|---|
| `greeting` | 只有寒暄，没有业务诉求 | “你好，在吗” | “你好，查一下退款”属于 `query` |
| `query` | 询问信息、原因、状态或流程 | “退款什么时候到账” | “退款没到账”属于 `report` |
| `request` | 要求系统执行操作或协助办理 | “帮我创建工单” | “工单一直没人管”属于 `complaint` |
| `report` | 陈述正在发生的故障或异常 | “宿舍WiFi连不上” | “为什么连不上”属于 `query` |
| `complaint` | 明确不满、投诉、久未解决 | “拖了一周还没处理” | 单纯报告一次故障不算投诉 |
| `feedback` | 改进建议或正面评价 | “建议增加余额提醒” | “帮我开启提醒”属于 `request` |
| `other` | 校园服务范围外或无法分类 | “推荐一部电影” | 校园故障报告不属于 `other` |

### Escalated（布尔值）

只有明确要求人工客服、真人、负责人、主管、老师介入或明确要求升级处理时为 `true`。单纯出现“紧急”“马上解决”不自动升级。

## 数据集

- 总计460条且消息文本无重复。
- 360条场景矩阵开发/验证数据。
- 100条由旧数据迁移而来的挑战测试数据。
- 每条包含 `review.status`、标注理由以及是否还需用户签字。
- 机器辅助复核不冒充领域专家人工签字；`requires_human_signoff=true` 的样本仍需项目负责人最终确认。

数据文件：`data/eval/intent_axes_golden.json`。

## 实验设计

对比两种方案：

1. `llm_only`：DeepSeek按三轴输出结构化JSON。
2. `llm_plus_safety_rules`：只对明确人工接管表达增加确定性升级兜底，不修改领域和动作。

业务门槛：

- Domain Macro-F1 ≥ 0.85
- Action Macro-F1 ≥ 0.80
- Escalation Recall ≥ 0.95
- Escalation Precision ≥ 0.85

运行命令：

```powershell
.\.venv\Scripts\python.exe tools\build_intent_axes_golden.py
.\.venv\Scripts\python.exe -u tools\run_intent_axes_eval.py all --batch-size 5 --concurrency 4
```

脚本逐批保存预测、支持断点续跑；连续格式错误时会自动拆小批次，并通过锁文件阻止两个进程覆盖同一检查点。
